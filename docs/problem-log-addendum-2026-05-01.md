## 问题 41：`qwen3` 系列在 compatible-mode 下对结构化输出和强制 `tool_choice` 的兼容要求不同

**状态**：已修复并完成端到端验证

**现象**

- 目的地 Router 在 `with_structured_output(...)` 下会报 `messages must contain the word 'json' ... to use response_format of type 'json_object'`。
- 住宿阶段在 thinking mode 下会报 `tool_choice parameter does not support being set to required or object in thinking mode`。
- 这两个问题在 `qwen-max` 时代不明显，切到 `qwen3.6-plus` 之后才被真实链路稳定暴露出来。

**根因**

- 项目之前默认把“结构化输出”和“强制工具调用”都当成所有模型通用的能力。
- 但 compatible-mode 只是接口兼容，不代表模型行为兼容；不同模型家族对 JSON schema、tool forcing、thinking mode 的约束并不一样。
- 这类差异如果散落在 Router、中间件、子 Agent 里，会让“换模型”退化成一次全项目排雷。

**怎么解决**

- 在 [app/utils/llm_factory.py](D:/Users/Administrator/PycharmProjects/ZhiXing/langgraph-travel-planner/app/utils/llm_factory.py) 增加统一能力描述：
  - `supports_forced_tool_choice`
  - `structured_output_requires_json_keyword`
- 在 [app/agents/routers/destination_router.py](D:/Users/Administrator/PycharmProjects/ZhiXing/langgraph-travel-planner/app/agents/routers/destination_router.py) 中让分类器提示词按模型能力补充显式 JSON 要求。
- 在 [app/core/middleware.py](D:/Users/Administrator/PycharmProjects/ZhiXing/langgraph-travel-planner/app/core/middleware.py) 中改成：
  - 支持强制 `tool_choice` 的模型继续走原逻辑
  - 不支持的模型改为在 `system_prompt` 中注入本轮工具引导，而不是硬塞 `tool_choice`
- 补回归测试 [tests/test_step_prompt_rendering.py](D:/Users/Administrator/PycharmProjects/ZhiXing/langgraph-travel-planner/tests/test_step_prompt_rendering.py)，让测试按模型能力分支断言。

**我的思考**

- 以后换模型不应该再是“改一大堆兼容问题”，而应该尽量收敛成“改模型名 + 少量能力配置”。
- 真正需要维护的不是“某个模型能不能跑”，而是“项目把模型差异收敛到了几个稳定入口”。
- 这次修完后，模型切换的风险仍然存在，但已经从“全仓库到处搜”降到了“优先检查 llm_factory 和少量提示词边界”。

## 问题 42：端到端链路虽然能降级运行，但 MCP 子进程在 Windows 上仍然存在偶发不稳定

**状态**：已记录，待优化

**现象**

- 在多次 `TestClient(app)` 端到端复核中，`weather` 和 `aigohotel-mcp` 偶尔会在 warmup 阶段短暂 unavailable，随后再次启动恢复。
- 日志里出现过：
  - Rust 层 `memory allocation failed`
  - `MemoryError`
  - `platformdirs` 相关 `OSError: [WinError -2147467259] 未指定的错误`
- 好消息是：当前主应用不会因为单个 MCP 子进程抖动而整体启动失败，系统能以 degraded mode 继续服务。

**根因**

- 问题不在主 Agent 业务逻辑，而在 Windows 环境下外部 MCP 子进程自身的稳定性和启动成本。
- 这些服务有的来自不同运行时栈（Python、Rust、外部 wheel/uv 缓存环境），在冷启动、并发启动和目录解析时更容易出边缘问题。
- 项目现在已经具备“服务降级”能力，所以故障被从“主流程直接崩溃”降成了“启动偶发抖动”，但问题本身还在。

**怎么改进**

- 给 MCP warmup 增加更明确的单服务重试和失败分类，区分“临时启动失败”和“确定不可用”。
- 把高成本或高抖动 MCP 的首次启动日志单独结构化，方便后面判断是资源不足、权限问题还是运行时兼容问题。
- 对酒店、天气这类非主链路致命能力，继续坚持 degraded 模式，不要重新耦合回全量阻塞 ready。
- 如果后续部署目标仍然主要是 Windows，本地启动成本较高的 MCP 最好考虑独立进程常驻，而不是每次随应用冷启动。

**我的思考**

- 这类问题很容易被误判成“模型不稳”或“Agent 乱调工具”，但真实根因其实在工具运行时层。
- 从工程角度看，能降级已经是第一步；第二步才是让降级变得可观测、可解释、可恢复。
- 这次复核最大的收获之一，是把“业务兼容问题”和“工具进程稳定性问题”明确分层了，后面优化就不会再混在一起。

## 问题 43：流式聊天里“像卡住了一分钟”很多时候不是工具慢，而是模型首个 token 本身很晚

**状态**：已确认，待继续优化

**现象**

- 2026-05-05 的两轮真实 SSE 复核里，同一个用户会话都出现了明显的“首字等待”：
  - 第一轮：总耗时约 `69s`，首个 token 约 `66.56s`
  - 第二轮：总耗时约 `77s`，首个 token 约 `67.23s`
- 第二轮甚至没有任何 `tool_call` 事件，说明那一轮长等待并不是 12306、酒店或天气工具造成的。
- 从用户视角看，这就会表现成“页面长时间只有等待态，像卡住了一样”，哪怕最终回答确实能生成出来。

**根因**

- 当前主链路里，模型在真正开始流式输出前就可能先消耗较长时间进行内部推理或状态判断。
- 之前前端的空白气泡会把这种延迟放大成“前端坏了”的错觉；虽然等待态展示已经修复，但服务端首 token 仍然偏慢。
- 这说明“工具慢”和“模型首字慢”是两类不同问题，不能混在一起判断。

**怎么观察**

- 在 [app/api/v1/chat.py](D:/Users/Administrator/PycharmProjects/ZhiXing/langgraph-travel-planner/app/api/v1/chat.py) 中新增了结构化埋点：
  - `SSE chat started`
  - `SSE first token emitted`
  - `SSE tool started / finished`
  - `SSE chat completed`
- 现在可以直接从日志里判断某一轮到底是“首 token 慢”，还是“某个工具慢”，还是“两者都慢”。

**我的思考**

- 这是一个非常典型的“体感问题和技术问题分离”案例。
- 用户只会说“它卡了”，但工程上至少要先分清楚是“卡在模型”、还是“卡在工具”、还是“卡在前端等待态”。
- 这轮最大的价值不是立刻把时间压到很短，而是终于把“慢”变成了可测量、可归因的问题。

**我的思考**

- 这类问题很隐蔽，因为日志看起来像是“交通慢”或“酒店慢”，但真实浪费发生在链路边缘的工具装配阶段。
- 这次修复说明，可选依赖不仅要从启动路径里拆出来，也要从无关业务路径里拆干净。

## 问题 45：目的地 Router 存在结构化输出长时间后失败的问题，会制造另一类“假卡死”

**状态**：已确认，待修复

**现象**

- 2026-05-05 直接调用目的地 Router 时，单次请求大约在 `139.77s` 后失败。
- 失败不是普通超时，而是结构化输出校验错误：
  - `ClassificationResult.classifications` 缺失
  - 实际返回里更像是模型给出了 `tool_calls` 风格的内容，而不是 Router 期望的结构化对象
- 从用户体感上看，这类问题也很像“它一直在转圈”，但和酒店超时、12306 查询慢并不是一类问题。

**根因**

- `classifier_node()` 依赖 `with_structured_output(ClassificationResult)`。
- 在当前模型行为下，分类器并不总能稳定返回 `{"classifications": [...]}` 这一目标结构。
- 这说明“补了 JSON 关键词”虽然解决了一部分兼容性问题，但并没有完全消除 Router 分类阶段的结构化漂移。

**怎么改进**

- 继续收紧 [app/agents/routers/destination_router.py](D:/Users/Administrator/PycharmProjects/ZhiXing/langgraph-travel-planner/app/agents/routers/destination_router.py) 的分类器输出约束。
- 必要时为分类器增加一层宽松解析/回退，把 `tool_calls` 风格或非标准 JSON 响应整理成 `ClassificationResult`。
- 把这类“分类失败但不是系统性故障”的情况也做成可解释降级，而不是让整段链路长时间后直接异常。

**我的思考**

- 这类问题比单纯“模型慢”更危险，因为它会同时消耗很长时间，又在最后阶段失败。
- 如果不把它和普通超时区分开，排查的人很容易把锅甩给网络、VPN 或外部工具。
- 这次把它单独拎出来之后，后面修目的地阶段就有了明确抓手，而不是继续凭感觉猜。 

## 问题 46：旅行规划主链路不适合“全流程只用一个模型”，更适合按步骤做 `plus + flash` 分工

**状态**：已落地第一版分工，待继续观察真实收益

**现象**

- 这个项目的链路并不是单一任务，而是混合了多种性质完全不同的步骤：
  - 需求收集与澄清
  - Router 分类与目的地判断
  - RAG 查询优化与重排
  - 交通、住宿、预算整合
  - 最终的完整行程规划与报告整理
- 之前全链路主要挂在 `qwen3.6-plus` 上，虽然质量比较稳，但真实复核里已经多次看到：
  - 首个 token 很慢
  - 轻量分类和补充性步骤也吃到了和主规划同等级别的成本
  - 用户体感上会把这种“每一步都慢一点”累积成“系统总在卡”

**根因**

- 旅行规划不是一个单模型最优问题，而是一个“不同子任务对模型能力诉求不同”的问题。
- 像需求收集、分类、RAG 改写这类步骤，本质更偏：
  - 短输出
  - 规则性强
  - 对延迟敏感
- 而主规划、复杂整合、最终报告这类步骤才更需要：
  - 更强的综合表达能力
  - 更长上下文稳定性
  - 更好的整体规划质量
- 如果所有步骤都统一走 `plus`，系统会为轻量任务支付不必要的时延和成本。

**为什么不是直接换成 `qwen-deep-research`**

- `qwen-deep-research` 更像深度研究/长报告工作流，不适合直接顶替实时聊天主模型。
- 这个项目当前更核心的诉求是：
  - 多轮对话中的快速推进
  - 工具调用与状态迁移的稳定配合
  - 在用户追问时持续保持响应
- 这些诉求和 deep-research 的最佳使用场景并不一致。
- 更合理的做法是：
  - 先把主链路实时体验优化好
  - 之后如有需要，再把它作为“最终旅游报告增强版”的独立后处理能力引入

**怎么改进**

- 已在代码里落地第一版模型分工：
  - `planner`: `qwen3.6-plus`
  - `router`: `qwen3.6-flash`
  - `rag`: `qwen3.6-flash`
  - `report`: `qwen3.6-plus`
- 具体调整点：
  - 在 [app/config.py](D:/Users/Administrator/PycharmProjects/ZhiXing/langgraph-travel-planner/app/config.py) 中把不同阶段的模型名独立成配置项
  - 在 [app/utils/llm_factory.py](D:/Users/Administrator/PycharmProjects/ZhiXing/langgraph-travel-planner/app/utils/llm_factory.py) 中增加按 profile 解析模型的能力
  - 主 agent 继续使用 `planner`
  - 目的地 Router 改用 `router`
  - RAG 查询优化与 reranker 改用 `rag`

**我的思考**

- 这是一个很典型的“系统慢，不一定是模型差，而是模型没有被放在合适位置”的问题。
- 真正高质量的多 Agent / 多步骤系统，很多时候不是靠“换一个更强的总模型”，而是靠“把合适的模型放到合适的环节”。
- 这次分工不是为了炫技，而是为了把两个目标拆开：
  - 轻量步骤尽量快
  - 关键规划步骤继续稳
- 后续如果这套分工在真实链路里表现稳定，再考虑把“报告生成”进一步往 deep-research 风格扩展，会比现在直接把它塞进主链路更稳。

## 问题 48：长等待不只是模型慢，目的地 RAG 链路本身也会把首字时间拖到两分钟左右

**我的思考**

- 这条问题很有代表性：用户看到的是“页面很久没出字”，但根因并不全在前端，也不全在模型。
- 如果不把服务端日志和链路耗时拆开，很容易误判成：
  - “只是前端假卡死”
  - 或“只是换个更快模型就行”
- 实际上，这类多工具旅行规划系统的首字时间，往往是：
  - 模型推理
  - 外部工具
  - RAG 检索
  - 结构化解析失败回退
  共同叠加出来的。
- 所以这次更合理的策略不是只盯模型，而是：
  - 前端先把等待体验做得更诚实
  - 后端再逐步把重链路拆薄。 

## 问题 49：路线预览触发过早，会把澄清消息撑得很长，并破坏流式阅读位置

**状态**：已修复前端触发门槛和流式滚动锚点

**现象**

- 真实测试时，几乎每条助手回复后面都会带一大块“路线预览”。
- 即使助手只是在确认预算、日期、同行人等细节，页面也会渲染地图路线工作区。
- 更糟的是，流式生成时前端会反复滚动到消息底部，用户最先看到的是路线预览尾部，而不是这条回复的开头。

**根因**

- `buildJourneyPreviewState(...)` 之前把“是否渲染路线预览”的条件设得太宽：
  - 只要文本里出现交通、住宿、景点等关键词，就容易被判定为有具体路线内容。
  - 澄清类问题虽然还没形成路线，但因为含有这些关键词，也被误判为可以显示地图。
- `addLoading(...)`、`convertLoadingToAssistant(...)`、`updateMessage(...)` 又都在强制 `scrollTop = scrollHeight`。
  - 这会让每次生成、每次更新都把用户拉到消息最底部。
  - 当消息尾部挂了很大的路线预览时，阅读体验就会显得“刚生成就跳到下面去了”。

**怎么解决**

- 新增了路线预览的二级门槛：
  - 澄清/确认类消息只显示摘要和结构化卡片，不显示地图路线工作区。
  - 只有出现明确的分日行程、最终报告、完整路线、地图路线等信号时，才渲染路线预览。
- 调整流式滚动策略：
  - 创建加载消息时滚到这条回复的顶部。
  - 后续流式更新不再反复强制贴底。
  - 最终把 loading 转成助手消息时，也锚定在该消息顶部。

**我的思考**

- 这个问题本质上不是“地图做得不好”，而是“地图出现的时机不对”。
- 地图路线是高密度信息，应该在用户进入规划成品阶段时作为增强，而不是在澄清阶段抢占视觉中心。
- 流式回复的滚动也一样，AI 生成中最重要的是让用户从当前回复开头读起，而不是追着尾部跑。

## 问题 50：强制“问题收尾”会让模型在用户已经授权后继续追问

**状态**：已收敛需求收集和餐饮阶段提示词

**现象**

- 用户已经说“没忌口，吃饭你看着安排”后，助手仍然会继续问“没问题吗/我就这么安排吗”。
- 这种回复看起来像是在问用户，但用户其实已经给出了授权，继续追问会显得重复、犹豫，也拖慢流程。

**根因**

- 需求收集阶段的全局风格规则里有一条“每次回复最后都用一个自然的问题收尾”。
- 餐饮阶段也默认先确认忌口，再问口味/用餐方式。
- 当用户用“没忌口/你看着安排/随便/按你推荐”这类口语表达授权时，提示词没有明确告诉模型这些表达等价于“可以直接推进”。

**怎么解决**

- 把强制问题收尾改成条件式问题：
  - 只有信息缺失、高风险决策或确实需要用户选择时才问。
  - 用户已经明确授权时，直接推进，不再重复问确认。
- 在餐饮阶段补充专门规则：
  - 用户说“没忌口/没有过敏/吃饭你看着安排/随便安排/按你推荐”时，视为已确认饮食安全和授权安排。
  - 用户已经说“都可以/没有了/你看着安排”时，不再继续问口味选择。

**我的思考**

- 对话式产品不是每轮都要问问题才显得“互动”。
- 真正好的互动应该区分“需要用户决策”和“用户已经把决策权交给系统”。
- 旅行规划里很多用户会用“你看着安排”表达信任，这时系统应该接住这个授权，给出可靠方案，而不是把问题又推回用户手里。

## 问题 51：酒店偏好被当成地点反复查询，可能触发 LangGraph 递归上限

**状态**：已加工具层兜底和住宿提示词约束；仍建议后续真实链路复核

**现象**

- 用户在住宿阶段输入“江景房”后，页面出现：
  - `Recursion limit of 25 reached without hitting a stop condition`
- 服务器日志显示，模型在同一轮里多次重复调用酒店查询：
  - `query_hotel_options`
  - `searchHotels`
- 类似“长沙湘江中路”这种过窄地点先查不到，后面又被模型不断换成“长沙”“长沙万达广场”“长沙开福区”等继续试。

**根因**

- 住宿阶段提示词鼓励“工具结果不理想时放宽区域再查”，但没有限制同一轮最多查询次数。
- 模型容易把用户补充的住宿偏好当成新的 `destination` 或 `place`，而不是写入 `preferences`。
- 酒店工具对“江景房”的理解偏窄，原来没有把“江景的房/靠江看景/河景/湖景/景观房”这类自然表达归一成水景或景观偏好。
- 地点候选也不够稳，例如“长沙湘江中路”没有自动加入“长沙”这种城市级兜底。

**怎么解决**

- 工具层：
  - 对“长沙湘江中路”这类具体区域，自动加入城市级候选“长沙”和英文别名 `Changsha`。
  - 对“江景房/江景的房/河景/湖景/景观房/靠江看景”等表达，统一推断为水景或景观偏好标签。
- 提示词层：
  - 住宿阶段同一轮最多调用一次 `query_hotel_options`。
  - 工具内部已经做放宽兜底，结果为空时不要继续循环查，先总结并告诉用户下一轮如何放宽。
  - 用户只补充房型/景观/安静/便利等偏好时，不能把这些偏好改写成新的目的地。

**我的思考**

- 这个问题比“查不到酒店”更危险，因为它不是单点失败，而是“查不到 -> 模型自发换参数 -> 再查 -> 再换参数”的循环。
- 对 Agent 系统来说，工具调用次数边界很重要，不能只靠模型自己判断何时停。
- 偏好和地点也必须拆清楚：用户说“江景房”是在描述想住什么，不是在说要把目的地改成“江景房”。

## 问题 52：最终报告不能只靠普通聊天文本，需要稳定章节和专用渲染层

**状态**：已新增前端报告渲染和后端报告结构约束

**现象**

- 最终报告此前基本还是普通聊天气泡里的长文本。
- 预算、每日行程、风险提醒、地图路线等信息混在一起，阅读上不像“旅行报告”，也不方便后续做导出、编辑或地图联动。

**根因**

- 后端订单/报告阶段只要求“提供最终旅行方案报告”，但没有稳定章节约束。
- 前端只有通用聊天文本、结构化卡片和路线预览渲染，没有专门识别最终报告并渲染为报告页的组件。
- 所以前端只能被动展示模型文本，模型格式稍微变化，最终效果就会不稳定。

**怎么解决**

- 后端提示词新增最终报告结构：
  - 行程概览
  - 交通与住宿
  - 预算明细
  - 每日行程
  - 景点地图
  - 天气与风险提醒
  - 后续可调整
- 前端新增 `renderTravelReport(...)`：
  - 识别“最终/完整/报告/个性化旅游规划”等报告信号。
  - 将报告渲染成报告封面、指标条、章节卡片、每日时间线和地图预览。
  - 在桌面端和手机端都避免横向溢出。

**我的思考**

- 报告页是整个旅行规划链路的“终点体验”，不能只靠模型写得好不好。
- 更稳的方式是让模型产出稳定章节，让前端把这些章节变成可视化结构。
- 这也为后续功能留了接口：比如导出 PDF、编辑每日行程、地图按天高亮、预算卡片可展开等。
