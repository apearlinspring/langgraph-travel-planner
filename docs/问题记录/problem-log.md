# 项目问题记录

这个文档从 2026-04-29 开始维护，用来沉淀推进过程中遇到的“值得记录”的问题。

记录原则：

- 不只记录表面报错，还记录为什么它值得重视。
- 每个问题都说明现象、根因、解决方式和后续思考。
- 已修复的问题也保留，因为它们往往能暴露项目结构上的薄弱点。

## 问题 1：酒店 MCP 的可执行入口写错了

**状态**：已修复

**现象**

- 酒店 MCP 已经在 `.env` 中配置了真实 Key，但实际拉起后返回 0 个工具。
- 单独探测时，`uvx` 能装包，但找不到真正的启动入口。

**根因**

- 包名是 `aigohotel-mcp`，但早期接线里把真正的可执行入口写成了 `aigohotel_mcp`。
- 这类问题最隐蔽的地方在于：配置“看起来很像对的”，而且不会在编辑器里直接报红，只会在运行时以“工具空列表”的方式表现出来。

**怎么解决**

- 将 MCP 启动参数修正为：
  - `uvx --from aigohotel-mcp aigohotel-mcp`
- 同时补了配置层单测，避免以后再次把包名和 CLI 入口混淆。

**我的思考**

- 这类问题说明项目当前对第三方 MCP 的接入，仍然偏“字符串拼接式”，缺少一层对外部依赖的显式契约校验。
- 后续如果再接新的 MCP，最好在接入当轮就补一条“最小可用性验证测试”：
  - 服务能拉起
  - 工具数量大于 0
  - 关键工具名存在
- 这样能把“接上了但其实没接通”的问题更早暴露出来。

## 问题 2：本地 MCP Server 启动到了系统 Python，而不是项目虚拟环境

**状态**：已修复

**现象**

- `weather_server.py`、`search_server.py` 在某些场景下会报依赖缺失，比如 `httpx`、`dotenv` 找不到。
- 但这些依赖明明已经安装在项目虚拟环境里。

**根因**

- MCP 配置里本地 stdio server 使用的是裸 `python`。
- 在 Windows 环境下，这很容易落到系统 Python，而不是 `.venv` 对应的解释器。

**怎么解决**

- 将 `weather` 和 `search` 两个本地 MCP server 的启动命令统一改为 `sys.executable`。
- 这样当前进程用哪个 Python，子进程就跟着用哪个 Python。
- 同时补了配置单测，确保这条约束不会被后续改坏。

**我的思考**

- 这是非常典型的“本地能跑但不稳定”的问题。
- 对依赖子进程的项目来说，解释器路径其实是核心配置，不应该默认相信 PATH。
- 后续如果还有本地 worker、脚本化 server、离线处理器，也建议统一走当前解释器路径，而不是用裸命令名。

## 问题 3：住宿阶段注入了记忆工具，但主 Agent 没注册这个工具

**状态**：已修复

**现象**

- 住宿阶段运行时会报错，大意是中间件追加了一个主 Agent 不认识的工具。
- 这会直接阻塞住宿阶段对话。

**根因**

- `StepConfigMiddleware` 在住宿阶段工具集中加入了 `update_accommodation_preference_tool`。
- 但 `create_travel_agent()` 的总工具注册列表里漏掉了它。
- 也就是说，“阶段工具集”和“主 Agent 全局工具注册表”发生了漂移。

**怎么解决**

- 将 `update_accommodation_preference_tool` 补进主 Agent 的总工具列表。
- 增加回归测试，确保创建 Agent 时该工具一定存在。

**我的思考**

- 这暴露出当前工具注册存在双份定义：
  - 一份在步骤配置里
  - 一份在主 Agent 创建处
- 双份定义很容易漂移。
- 后续更稳的做法，是让步骤配置成为单一事实来源，再由主 Agent 统一从步骤配置汇总工具，而不是手工双写。

## 问题 4：步骤 Prompt 用的是 Python 占位符，但中间件却按 Jinja 去渲染

**状态**：已修复

**现象**

- Prompt 里大量写了 `{selected_destination}`、`{user_requirement.departure_date}` 这类变量。
- 但模型实际收到的 prompt 里，这些值并没有被真正替换进去。
- 直接后果就是模型会重复问已经确认过的问题，看起来像“记不住上下文”。

**根因**

- Prompt 模板实际是 Python `str.format` 风格。
- 中间件却使用了 Jinja 渲染方式。
- 这不是一个小显示问题，而是整个 handoff 流里“状态注入”几乎都没有真正工作。

**怎么解决**

- 去掉 Jinja 渲染方式。
- 改为基于 `str.format_map` 的渲染逻辑。
- 对嵌套 dict 进行属性化包装，让 `{user_requirement.departure_date}` 这类路径可以被正确解析。
- 顺便补了 `origin_city`、`destination` 这类常用别名的自动映射。

**我的思考**

- 这是本轮最关键的结构性问题之一。
- 它说明“Prompt 看起来写完了”和“Prompt 真的吃到了状态”是两回事。
- 以后每次改步骤 Prompt，最好至少有一条非常小的自动化测试去验证：
  - 模板变量有没有被真正渲染
  - 渲染失败时是否会静默退化

## 问题 5：酒店 MCP 对中文地点名的召回不稳定，英文城市名更容易出结果

**状态**：已部分修复

**现象**

- 对 `北京`、`上海` 这类中文地点名直接搜索时，MCP 经常返回“搜索成功但酒店列表为空”。
- 改成 `Beijing`、`Shanghai` 后，同样的搜索条件却能直接拿到真实酒店。

**根因**

- 目前看，这更像酒店 MCP 上游的地点解析偏好问题，而不是我们代码的语法问题。
- 但从用户视角看，这仍然会表现成“中文用户输入正常，系统却查不到酒店”。

**怎么解决**

- 在项目内部增加一层 `query_hotel_options` 包装工具。
- 这层工具不再把复杂的 MCP 原始参数直接暴露给 Agent，而是：
  - 接受更贴近业务语义的参数
  - 先尝试原始中文地点
  - 若结果为空，再尝试去掉行政后缀后的地点名
  - 对常见热门城市追加英文别名兜底
- 同时把 MCP 原始返回做统一解析和格式化，减少模型处理原始 JSON 的负担。

**我的思考**

- 这个问题很有代表性：底层工具“可用”和用户体验“可用”之间，往往差一层业务适配。
- 如果把原始 MCP 直接交给 LLM，模型既要理解业务，又要拼复杂参数，还要自己处理工具怪癖，稳定性会明显下降。
- 适当增加一层项目内工具包装，不是多余抽象，而是在把不稳定边界往下压。

## 问题 6：当前状态机只能保存“住宿类型”，还不能保存“具体酒店”

**状态**：已修复基础链路

**现象**

- 住宿阶段已经能够给出真实酒店候选。
- 但当前状态里持久化的是 `selected_accommodation_types`，例如“星级酒店/民宿”，而不是“北京王府井天伦王朝酒店 / hotelId=43615”。
- 这意味着后续行程、预算、订单环节无法准确引用用户真正选中的酒店。

**根因**

- 当前住宿阶段最初的设计更偏“偏好确认”，不是“真实预订对象确认”。
- 现在项目能力增强到了真实酒店检索层，状态模型却还停留在更早的抽象层级。

**怎么解决**

- 已新增 `selected_accommodation_option`，用于保存用户最终确认的具体酒店。
- `query_hotel_options` 现在会把真实酒店候选写入 `accommodation_options`，包括 `hotel_id`、`name`、`location`、`price_per_night`、`rating`、`amenities`、`booking_url` 等信息。
- `select_accommodation_tool` 现在支持传入 `hotel_id` 或 `hotel_name`，并会优先从 `accommodation_options` 中找到对应酒店后写入 `selected_accommodation_option`。
- 回退到住宿规划之前的步骤时，会一并清空 `selected_accommodation_option`，避免后续流程误用旧酒店。
- 行程和预算的轻量生成工具已经开始读取具体酒店：
  - 行程里的住宿字段会使用已选酒店名。
  - 预算估算会优先使用已选酒店每晚价格。

**我的思考**

- 这是一个非常典型的“项目能力增长快于状态模型演进”的问题。
- 这次没有把住宿确认拆成两个独立工具，而是先让原有 `select_accommodation_tool` 兼容“偏好确认”和“具体酒店确认”两种输入，是为了降低对主流程和 prompt 的冲击。
- 后续如果继续做真实订单或预算精算，可以再把它拆成两个工具：
  - 一个确认住宿偏好
  - 一个确认具体酒店
- 这样能让状态模型更清晰，但不必在当前阶段一次性扩大改动面。

## 问题 7：测试用例对内部函数名有硬编码，重构后容易跟不上

**状态**：已修复

**现象**

- 新增酒店包装层后，默认回归里有一条测试直接失败。
- 失败不是因为业务逻辑错了，而是测试还在 mock 已被替换掉的 `get_hotel_tools`。

**根因**

- `tests/test_workflow_maintainability.py` 直接依赖了步骤配置模块里的具体函数名。
- 当实现从 `get_hotel_tools` 调整为 `get_hotel_followup_tools` 时，测试本身先失效了。

**怎么解决**

- 把测试中的 monkeypatch 目标同步切换到新的函数名。
- 同时保留“步骤配置应该覆盖所有 planning step”这个测试意图不变。

**我的思考**

- 这类问题说明测试已经开始部分依赖“实现细节”，而不是只依赖“行为契约”。
- 单元测试允许适度碰实现细节，但如果一改名字就大面积断裂，维护成本会慢慢抬高。
- 后续更稳的方向，是让这类测试尽量围绕“返回的 step config 结构”断言，而不是过多绑定内部 helper 的命名。

## 问题 8：航班 MCP 原始返回太长，不适合直接交给 Agent 消化

**状态**：已修复基础链路

**现象**

- VariFlight MCP 能正常返回 9 个工具，真实 Key 和服务链路可用。
- `searchFlightItineraries` 返回的是可读摘要，适合直接展示。
- `getFlightPriceByCities` 返回的是很长的 Python 风格结构化数据串，包含大量字段和舱位信息，如果直接交给 Agent，容易造成上下文浪费和提炼不稳定。

**根因**

- 航班 MCP 的工具粒度偏底层：有的工具适合展示，有的工具适合程序解析。
- 原来的 `flight_agent` 直接暴露一批原始 MCP 工具，并在 prompt 里猜工具名和参数结构；这会把“城市码转换、工具选择、长数据压缩、结果排序”都压给模型。

**怎么解决**

- 新增 `query_flight_options` 包装工具：
  - 支持中文城市名和 IATA 三字码。
  - 自动把常见城市转为 VariFlight 需要的城市码，例如北京 -> BJS、上海 -> SHA。
  - 调用 `searchFlightItineraries` 获取推荐摘要。
  - 调用 `getFlightPriceByCities` 获取结构化价格，再在代码里解析、排序、压缩为低价候选。
  - 输出统一的人类可读格式，并提醒价格和余票会波动。
- `flight_agent` 现在优先使用 `query_flight_options`，原始 MCP 工具只保留给航班号、舒适度、机场天气、中转等补充场景。
- `transport_coordinator` 的 `query_flights` 直接调用 `query_flight_options`，减少一层不必要的模型中转。

**我的思考**

- 这和酒店链路的问题很像：MCP 接上只是第一步，真正可用还需要一层业务语义包装。
- 对 Agent 来说，工具越接近用户意图，越稳定；工具越接近第三方 API 原始形态，越容易把模型变成“参数拼装器”和“长 JSON 摘要器”。
- 航班这种价格实时变化、字段多、可选舱位多的场景，更适合先由代码做确定性筛选，再让模型做解释和取舍。

## 问题 9：项目虚拟环境指向的 Python 不存在，恢复依赖又被 Windows 临时目录权限卡住

**状态**：已恢复可用，仍需后续清理

**现象**

- 运行 `.venv\Scripts\python -` 时出现 `Unable to create process using '"C:\Users\Administrator\AppData\Local\Programs\Python\Python312\python.exe" -'`。
- `.venv\pyvenv.cfg` 里的 `home` 指向了已经不可用的 Python 安装路径。
- 使用 `uv run` 尝试恢复时，`uv` 重新创建了 `.venv`，但 `uv sync` 在构建 `jieba==0.42.1` 时遇到 `PermissionError`。
- 后续搜索文件时，`.tmp` 和 `.uv-cache\builds-v0` 下也出现了权限拒绝目录，说明当前沙箱/Windows 临时目录权限状态不干净。
- 当前 `.venv\Scripts\python.exe` 能启动，但依赖不完整，例如 `langchain_mcp_adapters` 无法导入。

**根因**

- 原 `.venv` 绑定的是一条机器本地 Python 绝对路径，这条路径一旦被删除或移动，虚拟环境就会失效。
- `uv run` 在恢复过程中重建了 `.venv`，但依赖构建需要写临时目录和缓存目录；当前执行环境对部分临时目录没有写入或枚举权限。
- 这不是单个包的问题，而是“解释器路径、包缓存、构建临时目录”三者同时不稳定导致的环境问题。

**怎么解决**

- 首选方案仍然是在普通 PowerShell 中恢复环境，避免 Codex 沙箱对构建缓存目录的权限限制：

```powershell
$env:UV_CACHE_DIR="D:\Users\Administrator\PycharmProjects\ZhiXing\langgraph-travel-planner\.uv-cache"
$env:UV_PYTHON_INSTALL_DIR="D:\Users\Administrator\PycharmProjects\ZhiXing\langgraph-travel-planner\.uv-python"
$env:TEMP="D:\Users\Administrator\PycharmProjects\ZhiXing\langgraph-travel-planner\.tmp"
$env:TMP="D:\Users\Administrator\PycharmProjects\ZhiXing\langgraph-travel-planner\.tmp"
uv sync
```

- 如果 `.uv-cache\builds-v0` 或 `.tmp` 中残留的临时目录继续拒绝访问，需要先在确认没有任务运行后清理这些残留目录，再重新执行 `uv sync`。
- 恢复完成后，重新运行：
  - `.venv\Scripts\python -m compileall app tests`
  - `.venv\Scripts\python -m pytest -q`
  - 涉及 12306 的真实联调测试

**本轮实际恢复过程**

- `uv sync` 仍然会在 `jieba==0.42.1` 的 wheel 构建阶段失败，根因仍是 Python `tempfile` 创建出的临时目录无法写入。
- 采用项目内独立缓存 `.uv-wheel-cache`，先安装默认测试和 MCP/Agent 运行所需 wheel 依赖。
- 手动校准了 LangGraph 运行组合：`langgraph==1.0.5` 搭配 `langgraph-prebuilt==1.0.5`，避免 `ExecutionInfo` 导入错误。
- `jieba==0.42.1` 是纯 Python 包，已从 uv sdist 缓存中复制 `jieba/` 和 `jieba.egg-info/` 到 `.venv\Lib\site-packages`，绕过 wheel 构建。
- 继续补齐 RAG embedding 相关 wheel：`sentence-transformers`、`torch`、`scikit-learn`、`scipy`。
- 当前验证结果：
  - `pyproject.toml` 直接依赖审计：40 条全部已安装，0 缺失，0 版本不匹配。
  - `uv pip check`：无依赖冲突。
  - `.venv\Scripts\python -m compileall app tests`：通过。
  - `.venv\Scripts\python -m pytest -q`：`32 passed, 21 deselected`。

**补充审查**

- 一开始只按“关键模块可导入”恢复环境时，仍然留下了直接依赖版本漂移：
  - `prometheus-client==0.21.0` 缺失。
  - `langchain-core`、`python-multipart`、`PyJWT` 版本不符合 `pyproject.toml`。
- 将直接依赖校正后，又发现传递依赖层面还有冲突：
  - `langchain-openai 1.1.16` 要求 `langchain-core>=1.3.0`，但项目声明是 `langchain-core~=1.2.7`。
  - `langchain-text-splitters 1.1.2` 和 `langchain-classic` 至少要求 `langchain-core>=1.2.31`。
- 最终可用组合：
  - `langchain-core==1.2.31`
  - `langchain-openai==1.1.7`
  - `python-multipart==0.0.20`
  - `PyJWT==2.10.1`
  - `prometheus-client==0.21.0`
- 这次说明环境验证不能只看三件事之一，而要同时看：
  - 关键模块能否导入
  - `pyproject.toml` 直接依赖是否全部满足
  - `uv pip check` 是否无传递依赖冲突

**仍需注意**

- 当前环境已经可用，但不是一次干净的 `uv sync` 结果。
- 以后如果删除 `.venv` 重建，`jieba` 仍可能再次触发相同构建权限问题。
- 更长期的解决方向是：
  - 修复 Windows/sandbox 下 Python `tempfile` 创建目录的 ACL 异常。
  - 或在项目依赖策略中为 `jieba` 准备可复用 wheel / 替代安装方式。
  - 或在普通 PowerShell 环境中完成一次干净 `uv sync`，再把临时缓存残留清理掉。

**我的思考**

- 这个问题值得单独记录，因为它会让我们误以为“代码坏了”，但实际是运行环境半损坏。
- 对这个项目来说，MCP、LLM、RAG 都高度依赖虚拟环境的一致性；一旦 `.venv` 指向漂移，很多看似业务层的失败都会变成噪音。
- 后续可以考虑在 README 或启动脚本里增加一个环境健康检查，明确检测：
  - 当前 Python 是否来自项目 `.venv`
  - `langchain_mcp_adapters`、`fastmcp` 等关键依赖能否导入
  - `.env` 是否能被读取
  - MCP 关键服务是否能列出工具

## 问题 10：12306 原始工具参数复杂，直接交给 Agent 容易造成查询不稳定

**状态**：已修复基础链路，真实联调已验证

**现象**

- 12306 MCP 提供了城市/站名编码、直达余票、中转方案、经停站等多个工具。
- 原先 `train_agent` 把这些原始 MCP 工具直接交给模型，并在 prompt 中要求模型自己决定：
  - 先用城市还是车站名查编码
  - 是否能把中文地名直接传给余票接口
  - 什么时候查直达，什么时候查中转
  - 车型筛选和排序参数怎么传
- 这类链路在简单问答中可能能跑通，但在真实多轮规划里容易受模型参数拼装稳定性影响。

**根因**

- 12306 的底层工具更接近 API 能力，而不是业务语义能力。
- “北京到上海，明天高铁优先”这句话背后实际包含日期解析、站点编码、直达查询、中转兜底、结果压缩多个步骤。
- 如果全部交给 LLM 临场处理，任何一步参数猜错都会导致整段交通规划退化成口头建议。

**怎么解决**

- 新增 `query_train_options` 包装工具：
  - 接受 `origin_city`、`destination_city`、`departure_date`、`train_filter_flags`、`allow_transfer` 等业务语义参数。
  - 自动调用 `get-station-code-of-citys` / `get-station-code-by-names` 解析站点编码。
  - 优先调用 `get-tickets` 查询直达车次。
  - 当直达结果为空、无票或无直达时，自动调用 `get-interline-tickets` 查询中转/接续方案。
  - 对过长结果做截断，避免把整段原始返回直接塞给主 Agent。
- `train_agent` 现在优先使用 `query_train_options`，原始站点/经停工具只保留给追问和解释场景。
- `transport_coordinator` 现在直接调用 `query_train_options`，减少一层不必要的子 Agent 中转。

**我的思考**

- 这和酒店、航班链路的改造逻辑是一致的：原始 MCP 是能力入口，项目内包装工具才是稳定业务接口。
- 我更倾向于让代码负责“确定性强、参数结构强”的部分，让 Agent 负责“解释、比较、取舍”。
- 环境恢复后，已按以下重点完成真实 12306 联调验证：
  - 相对日期是否会被交通协调器正确校准为绝对日期
  - 城市名和具体站名是否都能解析到正确站点代码
  - 直达无结果时是否能稳定触发中转兜底
  - 返回内容是否足够短、足够可读，适合进入主旅行规划上下文

**补充验证**

- 环境恢复后，真实 12306 schema 校准发现 `trainFilterFlags` 只允许 `G/D/Z/T/K/O/F/S`。
- 早期默认值 `GDC` 中的 `C` 不合法，会导致 `get-tickets` 参数校验失败。
- 已将默认车型筛选改为 `GD`，语义上仍覆盖高铁/动车，且符合 12306 MCP 当前 schema。
- 真实探针还发现：`2026-05-10` 北京 -> 上海可正常返回车次，但 `2026-05-14` 这类较远日期会返回 `Cannot read properties of undefined (reading 'result')`。
- 这更像 12306 MCP 在超出预售期或无数据时没有做友好兜底；包装层已将此类上游异常转译为“可能超出预售范围/暂无数据”，避免直接暴露底层 JS 报错。

**状态**：已修复基础链路

**现象**

- 酒店、航班、12306 查询已经能返回真实候选，但后续 `generate_itinerary_tool`、`summarize_budget_tool`、`generate_order_tool` 仍然偏演示版。

  - `price`

- `generate_itinerary_tool` 现在会引用：

  - 餐饮偏好
  - 旅行风格

- 回退元数据也补充清理 `selected_transport_option` 和 `report`，避免用户回退后沿用旧方案。

**我的思考**

- 这一步很关键，因为“工具能查到真实结果”和“最终计划真正吸收了真实结果”是两件事。
- 我更倾向于让状态机保存“用户确认过的结构化事实”，而不是依赖模型在长上下文里回忆前文出现过的车次、酒店和价格。
- 当前实现还不是完整的高质量自然语言行程生成器，但已经把真实数据从查询阶段贯通到了行程、预算和订单报告阶段，后面可以继续在这个结构上做内容质量打磨。

## 问题 12：真实主 Agent 会话验证暴露了单工具测试发现不了的运行链路问题

**状态**：部分已修复，仍在真实会话中继续验证

**现象**

- 单独测试酒店、航班、12306 工具时可以通过，但直接跑主 Agent 多轮会话时，早期出现过 PostgreSQL checkpointer 连接池超时。
- Windows 默认 `ProactorEventLoop` 与当前 psycopg 异步连接池组合不稳定，真实脚本需要显式切换到 `WindowsSelectorEventLoopPolicy()`。
- PowerShell 直接传入中文测试语句时，部分命令链路会把中文变成 `??`，导致 Agent 收到的真实用户意图被破坏。
- 酒店 MCP 初次接入主 Agent 时失败，不是酒店 API Key 问题，而是子进程里的 `uvx` / FastMCP 仍尝试写入用户目录下的缓存和版本文件。
- 主 Agent 在一轮输入里可能连续完成需求记录、目的地确认、交通查询等多个步骤，这说明真实会话节奏和“每轮只走一步”的理想化测试不同。

**根因**

- 单工具集成测试只验证“这个工具能不能独立跑”，没有覆盖主 Agent、checkpointer、MCP 子进程、LLM 工具调用和状态推进同时发生的组合复杂度。
- Windows + sandbox 环境下，默认用户目录、临时目录、终端编码和事件循环策略都可能影响真实链路。
- MCP 子进程继承的环境变量如果不完整，就会绕开项目内缓存目录，回到 AppData 等不可控路径。
- 主 Agent 是由模型决定是否连续调用工具的，因此真实执行路径会受 prompt、上下文完整度和用户输入明确程度共同影响。

**怎么解决**

- 在 Windows 真实验证脚本和集成测试入口显式设置 `asyncio.WindowsSelectorEventLoopPolicy()`。
- 运行脚本时设置 `PYTHONIOENCODING=utf-8`，并在必要时用 Unicode escape 构造中文输入，避免命令行编码污染测试内容。
- 在 `app/mcp_core/client.py` 的 MCP 子进程环境构造中增加项目内默认目录：
  - `UV_CACHE_DIR=.uv-wheel-cache`
  - `UV_PYTHON_INSTALL_DIR=.uv-python`
  - `UV_TOOL_DIR=.uv-tools`
  - `FASTMCP_HOME=.fastmcp`
- 真实会话验证不只看最终回复文本，还要检查结构化状态字段，例如 `selected_transport_option`、`accommodation_options`、`selected_accommodation_option`、`budget` 和 `report`。
- 对“Agent 一轮推进多个阶段”的行为保持观察：如果用户信息非常明确，可以接受；如果它跳过用户确认，则需要再收紧阶段 prompt。

**我的思考**

- 这类问题很有价值，因为它们最容易制造“单测全绿，但真实产品不可用”的错觉。
- 对这个项目来说，能力增强不是单纯把 MCP 工具挂上去，而是要验证主 Agent 是否能在真实多轮上下文里稳定调用、保存、复用这些结果。
- 我更倾向于把真实链路验证脚本当成第五轮优化的“验收灯塔”：每修一块能力，都要回到主 Agent 会话里看它有没有真的穿过状态机并进入最终产物。

## 问题 13：真实会话里模型会用自然语言枚举、提前生成文本，甚至越过确认直接下单

**状态**：已做第一轮修复，仍需继续观察

**现象**

- 用户选择“上海城市酒店”时，模型第一次把住宿类型传成了中文“酒店”，`select_accommodation_tool` 拒绝后才改成 `star_hotel`。
- 用户选择“本地小吃和特色美食”时，模型第一次把餐饮类型传成“本地小吃/夜市、特色餐厅/名店”，`select_food_tool` 拒绝后才改成 `local/specialty`。
- 餐饮阶段结束后，模型在自然语言回复里生成了一份很完整的行程草案，但没有调用 `generate_itinerary_tool`，导致 `itinerary` 状态仍然是 `None`。
- 用户只要求“生成并记录最终行程，然后进入预算汇总”时，Agent 一路调用了 `generate_itinerary_tool`、`summarize_budget_tool`、`generate_order_tool`，没有等预算确认就生成订单。
- 订单阶段 prompt 里原本允许引导关注公众号/添加客服，导致最终回复额外出现没有事实来源的营销话术。

**根因**

- prompt 中展示给用户的是自然语言选项，但工具只接受英文枚举；模型在真实会话里很容易把“给用户看的标签”当成工具参数。
- 状态机工具和自然语言回复的边界不够硬：模型可以生成一段看似完整的最终内容，但没有写入结构化状态。
- `summarize_budget_tool` 执行后会把阶段推进到 `order_generation`，而订单阶段旧 prompt 又要求直接生成订单，导致同一轮里越过了预算确认。
- 订单 prompt 的“可以引导关注公众号、添加客服”等表述过于产品化，但项目没有真实公众号/客服信息，容易造成幻觉式营销补写。

**怎么解决**

- 在 `app/tools/state_transition.py` 增加中文别名归一化：
  - 交通：高铁/动车/火车 -> `train`，飞机/航班 -> `flight`，自驾/开车 -> `driving`
  - 住宿：酒店/星级酒店/中高档酒店 -> `star_hotel`，经济/快捷酒店 -> `economy_hotel`，民宿/客栈 -> `hostel`
  - 餐饮：本地小吃/夜市/扫街 -> `local`，特色餐厅/名店/特色美食 -> `specialty`，连锁/商场/省心 -> `chain`
- 在餐饮阶段 prompt 中明确：调用 `select_food_tool` 时必须传内部枚举；记录成功后只做短过渡，不要直接输出完整行程。
- 在行程阶段 prompt 中明确：用户要求生成/确认/记录最终行程时，必须调用 `generate_itinerary_tool`，不能只写自然语言版本。
- 在预算阶段 prompt 中明确：汇总预算后只展示预算和假设，除非用户同轮明确要求生成订单/最终报告/支付，否则不要继续下单。
- 在订单阶段 prompt 中明确：只有用户确认生成订单时才调用 `generate_order_tool`，并禁止添加无事实来源的公众号、客服微信、优惠活动等营销内容。
- 新增维护测试，覆盖中文交通/住宿/餐饮枚举归一化，并锁定订单 prompt 不再包含“公众号”。

**我的思考**

- 这是 Agent 项目非常典型的一类问题：人类可读话术越自然，工具参数越容易被模型“自然化”。
- 最稳妥的方式不是只靠 prompt 让模型记住枚举，而是在工具层接受常见自然语言并归一化；prompt 负责减少错误，工具层负责兜底。
- 行程、预算、订单这类最终产物必须以结构化状态为准。自然语言回复再漂亮，如果没有写入状态，下一步预算和报告就会变成“靠回忆工作”。
- 对下单这件事要特别谨慎：预算确认和订单生成之间应该有明确用户确认，不能因为状态机已经进入 `order_generation` 就自动推进。

## 问题 14：自驾路线由 LLM 直接解释高德原始 JSON，容易把秒级 duration 误读成小时

**状态**：已修复并完成回归验证

**现象**

- 交通协调器真实比较“北京 -> 上海”的航班、高铁、自驾时，确实同时调用了三路工具。
- 航班链路返回 193 条真实候选，低价约 400 元，最短耗时约 1 小时 45 分钟。
- 12306 链路返回 G1、G3、G549 等真实车次与二等座余票/价格。
- 自驾链路返回约 1222 公里，但最终回复写成了“约 48 小时 43 分钟”，明显不符合北京到上海的现实驾驶时间。
- 直接查看高德 `maps_direction_driving` 原始返回后发现：`distance=1222435` 米，`duration=48156` 秒，正确换算应约为 13 小时 23 分钟。

**根因**

- 原先交通协调器把自驾规划交给 `driving_subagent`，由 LLM 直接读取高德 MCP 原始 JSON 并生成自然语言。
- 高德路线里的 `duration` 字段单位是秒；模型看到 `48156` 时将其错误理解成了“48小时”，属于典型的单位解析错误。
- 自驾结果还包含大量路线步骤，长 JSON 增加了模型误读字段、截断或挑错重点的概率。

**怎么解决**

- 新增 `app/tools/driving_query.py` 包装工具 `query_driving_route`：
  - 调用 `maps_geo` 将出发地/目的地解析为经纬度。
  - 调用 `maps_direction_driving` 查询真实路线。
  - 由代码解析米和秒，并格式化为公里、小时分钟。
  - 按距离估算油费、过路费和每车总成本。
  - 提取少量主要道路，避免把完整原始 JSON 塞给模型。
- `transport_coordinator` 改为调用 `query_driving_route`，不再让自驾子 Agent 直接解释高德原始路线 JSON。
- 在交通协调器 prompt 中明确：自驾 duration 已由工具换算，不能再把原始秒数字段误读为小时。
- 新增单元测试锁定 `48156` 秒必须显示为 `13小时23分钟`，并确保摘要不出现 `48小时`。

**我的思考**

- 这次问题非常典型：MCP 工具“能返回真实数据”并不等于 Agent “能正确解释真实数据”。
- 对所有外部 API，凡是涉及单位、价格、字段嵌套、候选排序的部分，都应该尽量在代码包装层完成确定性解析。
- LLM 更适合做方案比较与用户解释，不适合直接承担“秒转小时、米转公里、字段单位判断”这种可确定计算。
- 这也强化了第五轮的方向：能力增强不是继续堆更多 MCP 工具，而是把关键 MCP 结果稳定地接进业务语义层。

## 问题 15：交通协调器相对日期校准仍可能先查错旧日期

**状态**：已修复并完成回归验证

**现象**

- 真实探针中，用户说“明天从北京到上海，坐高铁”。
- 协调器先调用了日期工具，拿到了当前日期 `2026-04-29`。
- 但第一次调用 `query_trains` 时仍传入了 `2023-11-22`，12306 返回 “The date cannot be earlier than today”。
- 随后模型又第二次调用 `query_trains`，这次才传入正确的 `2026-04-30`。
- 最终回答可用，但中间多了一次错误真实 API 调用，且暴露了模型在相对日期换算上的不稳定。

**根因**

- 原先 prompt 要求“相对日期先用日期工具校准”，但真正的日期换算仍由 LLM 自己完成。
- LLM 在复杂工具调用上下文里可能凭旧示例、训练记忆或上下文噪声生成错误绝对日期。
- 12306、航班这类真实 API 不应该接受模型猜出的过去日期，否则既浪费调用，也可能让最终回复混入错误上下文。

**怎么解决**

- 新增 `app/utils/date_normalization.py`：
  - 支持 `今天/明天/后天/大后天` 等常见中文相对日期。
  - 支持从“明天出发”“后天上午”“大后天去上海”这类短语中提取相对日期标签。
  - 支持合法 `YYYY-MM-DD`。
  - 拒绝早于今天的日期，并给出明确错误信息。
- 在 `transport_coordinator` 内部的 `query_flights` / `query_trains` 工具入口先做日期归一化。
- prompt 调整为：`query_flights/query_trains` 可以直接接收相对日期，不要让模型自己猜绝对日期。
- 新增单元测试，锁定 `2026-04-29` 下 `明天 -> 2026-04-30`，并拒绝 `2023-11-22` 这类过去日期。
- 真实重测“明天从北京到上海，坐高铁”后，协调器只调用了一次 `query_trains`，并传入 `2026-04-30`，没有再出现 `2023-11-22` 这类旧日期探针。

**我的思考**

- 这和自驾 duration 问题同源：日期换算是确定性逻辑，不应该交给模型临场发挥。
- 更好的边界是：用户语言可以自然，工具参数可以宽容，但进入真实 API 前必须经过代码校验。
- 对真实交通链路来说，本地拦截错误日期比让 12306/航班 API 报错更好，因为它能减少噪声并保护最终推荐质量。

## 问题 16：PowerShell 内联脚本里的中文输入可能被编码成问号，导致真实探针失真

**状态**：已规避

**现象**

- 真实验证交通协调器时，第一次用 PowerShell here-string 直接写中文测试问题。
- Agent 收到的用户内容被污染成一串问号，最终回复变成“您的消息中可能包含无法识别的字符”。
- 工具调用列表为空，导致这次探针无法反映真实交通协调器能力。

**根因**

- 当前 Windows PowerShell 执行内联 Python 脚本时，脚本文本编码和 Python 标准输入解码之间存在不一致。
- 即使设置了 `PYTHONIOENCODING=utf-8`，它主要影响 Python 的输入输出编码，不一定能修复 PowerShell 传入脚本文本时的源字符串编码问题。
- 对真实 Agent 探针来说，输入层一旦被污染，后面的工具调用和推荐质量判断都会失真。

**怎么解决**

- 后续在 PowerShell 内联 Python 探针中，中文用户问题统一写成 Unicode 转义字符串，例如 `\u660e\u5929`。
- 保留 `PYTHONIOENCODING=utf-8`，用于确保输出 JSON 和中文日志可读。
- 如果探针结果出现“无法识别字符”“全是问号”这类回复，优先怀疑脚本输入编码，而不是业务逻辑。

**我的思考**

- 这是很容易误判的验证问题：它看起来像 LLM 或工具链失效，实际是测试输入在进 Agent 前就坏了。
- 真实链路验证要特别注意“探针本身”的可靠性，否则会把环境噪音当成业务回归。
- 对这个项目来说，后续如果沉淀真实探针脚本，最好保存为 UTF-8 `.py` 文件或全部使用 ASCII 安全输入，避免临时 here-string 反复踩坑。

## 问题 17：交通协调器开放比较时可能重复查询，航班原始推荐摘要也可能带入高价公务舱噪音

**状态**：已修复并完成真实探针验证

**现象**

- “北京到广州，比较飞机、高铁和自驾”真实探针中，协调器第一次已经查询了航班、高铁和自驾，但随后又重复查询了一次航班和高铁。
- “北京到广州，坐飞机”真实探针里，航班最终回复混入了高价公务舱推荐，例如 `7650` 元级别的候选。
- 这两类问题不一定导致最终推荐方向错误，但会增加真实 API 调用成本，并让用户以为高价公务舱也是默认推荐项。

**根因**

- 协调器 prompt 只要求“按交通方式调用工具”，没有明确要求同一轮、同一路径、同一日期、同一方式不要重复查询。
- 航班包装工具原样保留了 VariFlight MCP 的自然语言推荐摘要；该摘要可能包含“其他推荐航班”长列表，其中会混入公务舱或高价票。
- 结构化低价候选本身是可控的，但原始推荐摘要抢在结构化候选前进入上下文，影响了最终回答质量。

**怎么解决**

- 在 `transport_coordinator` prompt 中增加约束：同一轮内，同一出发地/目的地/日期/方式只调用一次对应工具；除非工具明确失败或用户要求刷新，不要重复查询。
- 在 `app/tools/flight_query.py` 增加 `_compact_itinerary_summary`：
  - 保留“查询到多少航班、最低价、最短耗时”等摘要信息。
  - 截掉“其他推荐航班、推荐航班、航班列表、更多航班”等长列表。
  - 具体候选仍由结构化价格数据排序输出，优先展示低价经济舱候选。
- 更新航班单元测试，确保原始摘要中的 `公务舱 7650 元` 不会透传到工具结果。
- 真实复测后，长途开放比较只调用 `query_flights`、`query_trains`、`plan_driving_route` 各一次；航班回复不再包含 `7650` 或“公务舱”噪音。

**我的思考**

- 这个问题说明“真实 API 可用”之后，还要继续打磨“推荐语义质量”和“调用经济性”。
- LLM 适合综合比较，但不适合直接决定哪些原始候选该进入推荐池；高价公务舱这类噪音应该在包装层就压掉。
- 对未来的酒店、门票、餐厅链路也一样：第三方原文摘要可以作为参考，但真正进入主 Agent 上下文的内容应当经过项目内的业务筛选。

## 问题 18：订单生成后长期记忆保存失败可能覆盖最终报告，且工具会生成假的支付链接

**状态**：已修复并完成真实主 Agent 回归验证

**现象**

- 预算阶段回归中，用户只说“进入预算汇总，先不要生成订单”时，Agent 现在能正确只调用 `summarize_budget_tool`，不会提前下单。
- 但用户第二轮明确说“预算可以，请生成最终报告和订单”后，Agent 调用了 `generate_order_tool`，随后又调用 `add_travel_record_tool`。
- 当前探针状态没有 `user_id`，记忆工具返回“未识别到用户身份，无法保存出行历史”，最终可见回复被这句失败提示盖过，用户看不到完整订单报告。
- `generate_order_tool` 还会生成 `https://pay.example.com/{order_id}` 这类示例支付链接，容易被误解为真实支付入口。

**根因**

- 订单阶段 prompt 要求订单生成后调用长期记忆工具，但长期记忆写入属于旁路副作用，不应该影响最终用户可见主结果。
- 订单阶段工具列表暴露了 `add_travel_record_tool`，模型会把“保存历史”当成订单阶段的一部分继续执行。
- 当前项目没有真实支付服务，但订单工具用示例域名拼出了一个看似可点击的支付链接，这属于产品语义上的假能力。

**怎么解决**

- 从 `order_generation` 阶段工具列表中移除 `add_travel_record_tool`，订单阶段只负责生成最终方案和订单。
- 修改订单阶段 prompt：
  - 不调用长期记忆工具。
  - 不让记忆保存结果覆盖最终报告。
  - 没有真实支付能力时不要编造支付链接。
- 修改 `generate_order_tool`：
  - 不再输出 `pay.example.com`。
  - 明确展示“当前项目未接入真实支付服务，暂不生成支付链接”。
- 新增维护测试，锁定订单阶段不暴露 `add_travel_record_tool`，并确保订单消息不包含 `pay.example.com`。
- 真实主 Agent 回归验证：
  - 第一轮只请求预算：只调用 `summarize_budget_tool`，`order_id/report` 不生成。
  - 第二轮明确确认订单：调用 `generate_order_tool`，生成 `order_id/report`。
  - 最终回复不再出现记忆保存失败，也不再出现假支付链接。

**我的思考**

- 这个问题的本质是“主路径结果”和“旁路副作用”没有隔离。订单报告是用户显性目标，记忆保存只是锦上添花，不能反客为主。
- 真实支付、真实客服、真实订单履约这些能力，要么明确接入，要么明确标记未接入，不能用示例链接假装已经具备。
- 后续如果要保存出行历史，更适合放在后端确定性流程里：订单生成成功后由服务层在有 `user_id` 的情况下静默写入，失败只打日志，不打断用户结果。

## 问题 20：交通协调器在家庭行李和无票场景下的推荐质量不够稳

**状态**：已修复并完成真实探针验证

**现象**

- 矩阵验证中，短途“上海 -> 杭州，两个大人带一个孩子和两个行李箱，想省心”第一次只查询了高铁，没有查询自驾路线。
- 这会漏掉“门到门、行李多、带娃”的便利性对比；即使最终仍推荐高铁，也应该知道自驾成本和时长后再做判断。
- “北京 -> 上海，想尽量省钱但不想太折腾”第一次推荐了高铁二等座，但真实结果显示二等座无票，只有高价商务座等少量可用选择。
- 这类推荐会让用户感觉“推荐了一个买不到的便宜方案”，真实可执行性不足。
- 在一次复测中，模型还重复查询了航班和高铁各一次，说明单靠旧 prompt 的“不要重复查询”约束不够稳定。

**根因**

- 原 prompt 对“短途更建议高铁”的规则比较强，但没有把带娃、老人、行李多、门到门这类便利性信号提升为自驾对照触发条件。
- 模型容易把“参考票价”当成“可用票价”，没有足够明确地区分无票/无座/高价商务座与真正可推荐方案。
- 交通协调器温度为 `0.7`，在工具选择和总结环节有一定随机性，更容易重复调用同一路径同一日期的工具。

**怎么解决**

- 将交通协调器模型温度从 `0.7` 降到 `0.2`，让工具选择和推荐更稳定。
- 强化 `transport_coordinator` prompt：
  - 同一轮同一出发地/目的地/日期/方式只调用一次工具。
  - 工具返回结果后直接基于已有结果总结，不要为了确认最低价、余票、耗时再次调用同一工具。
  - 用户提到带孩子、老人、行李多、门到门、省心、不想折腾时，即使短途也要查询自驾作为便利性对照。
  - 当前无票、仅无座、只有高价商务座的火车方案不能作为首选，只能作为候补/刷新/改签日期备选。
  - 最终推荐必须提醒票价、余票、路况等实时信息会变化，正式购票或出发前需要再次核实。
- 增加维护测试，锁定低温度和这些关键 prompt 规则。
- 真实复测结果：
  - 家庭行李短途场景调用 `query_trains + plan_driving_route`，并基于自驾时长/成本和高铁余票做了更完整的省心判断。
  - 省钱不折腾场景只调用 `query_flights + query_trains` 各一次，推荐可买到的低价直飞航班，不再把无票高铁二等座作为首选。

**我的思考**

- 交通推荐的关键不是“哪种交通理论上最便宜”，而是“用户明天真的能不能买到、坐起来是否符合偏好”。
- 无票低价方案不应该抢占首选位置，它最多是候补策略；真实可执行性要优先于纸面性价比。
- 带娃、老人、行李多这种信号会改变“省心”的定义：高铁快不一定等于全程最省心，门到门成本和搬运行李也要进入比较。
- 这轮也说明交通协调器更适合低温度运行，因为它主要承担真实工具编排和方案权衡，而不是创意写作。

## 问题 21：目的地阶段的信息没有结构化沉淀，导致后续行程仍像通用模板

**状态**：已修复基础版本，并完成本地回归验证

**现象**

- 目的地阶段虽然可以通过目的地查询工具得到天气、景点、简要描述等信息，但用户确认目的地后，状态机只记录了 `destination` 这个字符串。
- 后续 `generate_itinerary_tool` 生成行程时只能根据目的地、天数、交通、酒店做通用模板，容易出现“第 1 天抵达并自由活动、第 2 天深度游”这类泛化内容。
- 最终报告已经能复用 itinerary/budget，但 itinerary 本身缺少目的地上下文时，报告质量仍会被上游模板限制。

**根因**

- `query_destination_info` 的结果主要停留在自然语言回复里，没有被结构化写入 `TravelState`。
- `select_destination_tool` 的职责过窄，只保存目的地名称，没法承接目的地阶段已经查到的天气、景点、费用估计等事实。
- `generate_itinerary_tool` 缺少一个稳定的数据入口来读取目的地候选信息，只能靠通用兜底逻辑生成每日安排。

**怎么解决**

- 扩展 `select_destination_tool`，在保持兼容旧调用的前提下，新增可选字段：
  - `description`
  - `weather_info`
  - `attractions`
  - `estimated_cost`
- 当这些字段存在时，将它们写入 `destination_options`，形成一份与已选目的地绑定的结构化上下文。
- 强化目的地阶段 prompt：模型调用 `select_destination_tool` 时，应尽量把已查询到的描述、天气、景点和可靠费用估计一并传入。
- 扩展 `generate_itinerary_tool`：
  - 优先从 `destination_options` 中找到当前目的地的上下文。
  - 将景点名称注入每日 `activities`，避免只输出泛化行程。
  - 将天气信息写入 `plan_b`，让备选方案更贴近真实目的地条件。
- 增加维护测试：
  - 验证 `select_destination_tool` 可以持久化目的地上下文。
  - 验证行程生成会使用 `外滩`、`上海博物馆` 等景点，并把 `阵雨` 等天气信息写入 Plan B。

**我的思考**

- 这类增强的核心不是“让模型更会写”，而是让状态机更会保存事实。只要事实没有结构化沉淀，后面的 Agent 再聪明也只能靠上下文回忆，稳定性会很差。
- 目的地、酒店、交通、餐饮都应该遵循同一个原则：第三方工具返回的原始信息可以很丰富，但真正跨阶段传递的内容必须被整理成项目内部可控的数据结构。
- 当前修复是基础版，已经把天气和景点打通到行程层；下一步如果要继续提升质量，更适合把景点、餐厅、开放时间、地理位置、门票和通勤时间进一步结构化，而不是继续堆 prompt。

## 问题 22：真实主 Agent 链路中目的地查询结果没有稳定写入 destination_options，且 Weather MCP 返回 list 时会失败

**状态**：已修复并完成真实主 Agent 探针复测

**现象**

- 本地工具测试可以证明 `select_destination_tool` 支持写入 `destination_options`，但真实主 Agent 探针中，模型调用了 `query_destination_info` 和 `select_destination_tool` 后，最终状态里的 `destination_options` 仍然是 `null`。
- 同一轮探针里，目的地 Router 的 Weather MCP 节点报错：`'list' object has no attribute 'get'`。
- 第二轮用户要求“基于已查到的信息生成行程”时，主 Agent 已经处在 `transport_planning`，因此它按流程继续询问交通偏好，而不是跳到行程阶段；这个行为本身符合状态机约束，但暴露出目的地阶段如果不稳定写状态，后续更难复用真实上下文。

**根因**

- 原设计把“把天气/景点传给 `select_destination_tool`”主要交给模型执行。真实链路中模型可能只传 `destination`，即使 prompt 写了“尽量传入 description/weather_info/attractions”，也不能保证每次执行。
- `query_destination_info` 只返回自然语言报告，不更新状态。也就是说，真正拿到目的地事实的工具没有负责落库，反而要求后续模型再手动转抄一次。
- Weather MCP 的真实返回可能是 list 包裹的 payload，而 `_format_weather_summary` 只按 dict 处理，直接调用 `.get()` 导致失败。

**怎么解决**

- 在目的地 Router 中新增天气 payload 归一化：
  - 如果 Weather MCP 返回 list，就取其中第一个 dict 作为天气 payload。
  - 如果返回 dict，则保持原逻辑。
  - 如果返回其他类型，则转成可读错误，避免抛出 `'list' object has no attribute 'get'` 这类内部异常。
- 扩展 `query_destination_info`：
  - 接收 `ToolRuntime`。
  - 在返回综合报告的同时，从报告中提取目的地描述、天气摘要和景点列表。
  - 通过 `Command(update=...)` 把这些信息写入 `destination_options`。
  - 保留无 runtime 时直接返回字符串的兼容行为，避免破坏单独调用工具的场景。
- 增加维护测试：
  - Weather MCP 返回 list payload 时仍能正常生成天气摘要。
  - `query_destination_info` 的上下文提取可以生成包含上海天气和景点的结构化目的地信息。
- 真实主 Agent 复测结果：
  - 工具调用链包含 `query_destination_info` 和 `select_destination_tool`。
  - 最终状态进入 `transport_planning`。
  - `selected_destination` 为 `上海`。
  - `destination_options` 已真实写入，包含 `上海`、天气摘要，以及 `外滩`、`豫园`、`田子坊`、`东方明珠` 等景点。

**我的思考**

- 这次问题很典型：prompt 可以引导模型做正确动作，但不能把“跨阶段状态一致性”完全押在模型自觉上。谁拿到事实，谁就应该优先负责结构化落库。
- Query 工具不一定只能“回答问题”，在 Agentic 状态机里，它也可以承担“把查询结果沉淀为候选状态”的职责。这样后续确认工具只需要确认选择，不必再承担转抄事实的负担。
- 真实 API/MCP 的返回结构经常比文档或 mock 更松散，工具边界层要尽量做 payload 归一化；否则一个 list/dict 差异就会让上层 Agent 误以为“天气不可用”。

## 问题 23：行程阶段真实主 Agent 会先输出自然语言草案，但不调用 generate_itinerary_tool 写入状态

**状态**：已修复并完成真实主 Agent 探针复测

**现象**

- 在已预置目的地、交通、酒店、餐饮和 `destination_options` 的情况下，用户明确要求“生成并记录最终行程”。
- 主 Agent 输出了一份看起来很完整的上海 3 天游程草案，包含上海博物馆、豫园、田子坊等内容。
- 但工具调用列表为空，`itinerary` 仍然是 `null`，预算和报告阶段无法复用这份自然语言行程。

**根因**

- 行程阶段 prompt 的前半部分强调“先给行程总览、输出每日行程、再问用户是否微调”，后面才写“用户确认后必须调用 `generate_itinerary_tool`”。
- 真实模型更容易优先执行前面的草案输出流程，把“生成并记录最终行程”理解成“先写一份最终草案给用户看”。
- 这再次说明：对状态写入类动作，prompt 里晚出现的约束不够稳定，必须把工具调用规则放在阶段最前面。

**怎么解决**

- 在 `itinerary_generation` prompt 顶部新增“硬性工具规则”：
  - 用户明确说生成行程、记录行程、最终行程、确认行程、就按这个来、可以了、满意时，必须先调用 `generate_itinerary_tool`。
  - 不要先输出长篇自然语言行程草案。
  - 工具调用成功后，再简要概述已记录的行程重点，并询问是否进入预算汇总。
  - 只有用户只是想先看草案/构思时，才允许输出自然语言草案。
- 调整任务流程顺序：第 1 步先判断用户意图，已确认则立即工具落库，未确认才进入草案模式。
- 增加维护测试，锁定 prompt 必须包含“必须先调用 `generate_itinerary_tool`”和“不要先输出长篇自然语言行程草案”。
- 真实主 Agent 复测结果：
  - 工具调用链包含 `generate_itinerary_tool`。
  - `itinerary_days` 为 3。
  - 行程内容包含 `外滩` 和 `上海博物馆`。
  - `plan_b` 包含天气提醒：`2026-05-20 可能有阵雨`。
  - `current_step` 正确推进到 `budget_summarization`。
  - `budget` 仍为 `null`，`order_id` 仍为 `null`，说明没有提前预算或下单。

**我的思考**

- 这类问题特别容易被“自然语言看起来很好”掩盖。对 Agent 项目来说，真正完成不是回复里写了什么，而是状态里是否有后续步骤能读到的结构化结果。
- 行程、预算、订单三个阶段尤其要坚持“最终产物必须由工具写状态”。自然语言可以负责解释和确认，但不能替代状态机。
- 后续验证预算和报告质量时，也要继续用同样标准：不仅看回复是否像预算/报告，还要检查 `budget`、`report`、`order_id` 是否在正确时机被写入，且没有提前越级。

## 问题 24：预算阶段能写入 budget，但可见回复可能省略预算匹配和关键假设

**状态**：已修复并完成真实主 Agent 探针复测

**现象**

- 在已预置真实交通价格、酒店价格、餐饮偏好和 itinerary 的情况下，用户明确要求“只做预算，不要生成订单或最终报告”。
- 主 Agent 正确调用了 `summarize_budget_tool`，`budget` 被写入状态，`order_id/report` 仍为空，说明流程边界是正确的。
- 但第一次复测中，可见回复只展示了费用明细和一段口语化解释，没有稳定保留“预算匹配”和“关键假设”这两个结构化部分。

**根因**

- `summarize_budget_tool` 原本只输出总计、人均和分类费用，没有在工具消息里直接写出预算匹配判断与关键假设。
- 预算阶段 prompt 只说“调用后展示预算明细和关键假设”，但没有要求可见回复必须保留固定结构。
- 模型会把工具结果改写成自然语言摘要，内容方向大致正确，但结构不稳定，不利于后续检查和用户决策。

**怎么解决**

- 扩展 `summarize_budget_tool`：
  - 增加 `assumptions` 局部变量并继续写入 `budget.assumptions`。
  - 调用已有 `_format_budget_fit`，在预算阶段直接生成“预算匹配”判断。
  - 工具消息中加入“预算匹配”和“关键假设”两个部分。
- 强化 `budget_summarization` prompt：
  - 用户要求汇总/查看预算时，必须调用 `summarize_budget_tool` 写入结构化 `budget`。
  - 工具调用后，可见回复必须保留“预算匹配”和“关键假设”小标题。
  - 不要把工具结果改写成只剩口语说明。
  - 除非用户同轮明确要求生成订单/最终报告/支付，否则不要继续生成订单。
- 增加维护测试，锁定预算工具消息与预算 prompt 都包含“预算匹配”和“关键假设”。
- 真实主 Agent 复测结果：
  - 工具调用链包含 `summarize_budget_tool`。
  - `budget.total` 为 `5672.0`，`budget.per_person` 为 `2836.0`。
  - `order_id` 和 `report` 仍为 `null`。
  - 可见回复包含“预算匹配”和“关键假设”。

**我的思考**

- 预算阶段不仅要“算出数字”，还要解释这些数字是否符合用户预期。比如人均 2836 元虽然低于预算上限，但也低于用户给定的预算区间下限，这代表可以考虑升级体验，而不是简单说“省钱成功”。
- 对用户决策最有价值的往往不是总价，而是“这个总价基于哪些假设、哪些部分最容易波动、如果不满意该调哪一块”。
- 这轮也延续了前面的经验：结构化工具结果和可见回复都要守住关键字段。只写进状态但用户看不到，会降低体验；只写给用户但状态没有，也会断掉后续链路。

## 问题 25：订单阶段不下单复核时缺少状态摘要，容易输出占位符式内容

**状态**：已修复并完成真实主 Agent 探针复测

**现象**

- 在 `order_generation` 阶段，状态里已经有 itinerary、budget、真实交通和酒店信息。
- 用户明确说“复核预算和关键风险，不要生成订单或最终报告”。
- 主 Agent 没有调用 `generate_order_tool`，也没有生成 `order_id/report`，流程边界是正确的。
- 但第一次真实探针中，可见回复出现了“[根据之前的对话填写]”这类占位符，说明模型没有稳定读到或复述当前状态里的预算、交通、住宿明细。

**根因**

- 订单阶段 prompt 只描述了“不要直接生成订单、先复述预算结论”，但没有注入已确认方案摘要。
- `StepConfigMiddleware` 之前只提供了住宿摘要，缺少统一的交通摘要、行程摘要和预算摘要。
- 在不调用工具的场景下，模型只能依赖消息上下文和泛化模板，因此容易输出空模板，而不是引用状态事实。

**怎么解决**

- 扩展 `StepConfigMiddleware`，新增动态 prompt 变量：
  - `selected_transport_summary`：包含具体车次/航班/路线、时间、耗时、价格和来源。
  - `itinerary_summary`：按 Day 提取主题和核心活动。
  - `budget_summary`：提取交通、住宿、餐饮、景点/体验、其他、总计、人均和关键假设。
- 更新订单阶段 prompt：
  - 注入“已确认方案摘要”，包含交通、住宿、行程和预算。
  - 用户只复核预算/风险时，必须基于摘要复述，不要生成订单。
  - 禁止输出“[根据之前的对话填写]”这类占位符。
- 增加维护测试，验证中间件能把 G1、上海城市酒店、Day 1 行程、总计 5672 元和关键假设渲染进系统提示词。
- 真实主 Agent 复测结果：
  - 未调用任何工具。
  - `order_id` 和 `report` 仍为 `null`。
  - 可见回复不再包含占位符。
  - 可见回复包含 `G1`、`上海城市酒店` 和 `5672` 等已确认状态信息。

**我的思考**

- 订单阶段有两种完全不同的任务：一种是“确认后生成最终报告/订单”，另一种是“确认前复核方案”。前者适合调用工具，后者更依赖 prompt 中的状态摘要。
- 这说明不是所有正确行为都等于调用工具；有些场景正确行为恰恰是不调用工具，但这时系统提示词必须给足状态事实，否则模型会用模板补洞。
- 中间件层统一生成摘要很有价值：它能让每个阶段在不调用工具时也有可靠上下文，减少“自然语言回复脱离状态”的风险。

## 问题 26：行程和最终报告已能贯通状态，但交付内容仍偏摘要，不像真实可执行方案

**状态**：已完成第一轮系统性内容质量增强

**现象**

- 目的地、交通、酒店、餐饮、行程、预算和最终报告链路已经能写入结构化状态。
- 但 `generate_itinerary_tool` 生成的 itinerary 主要是活动列表，缺少清晰的上午/下午/晚上安排、动线说明和风险提示。
- `generate_order_tool` 的最终报告虽然包含行程亮点、预算明细和核验提醒，但整体更像订单摘要，不像一份可以直接交付给用户执行的旅行方案。

**根因**

- `ItineraryDay` 原结构只要求 `activities/meals/accommodation/transport_note/plan_b`，没有明确承载时间段、动线和风险说明。
- 最终报告只提取了 itinerary 的亮点摘要，没有展开每日行程细节。
- 预算部分有数字，但最终报告里缺少“费用依据”和“可调整项”，用户看完后不容易判断下一步该怎么改。

**怎么解决**

- 扩展 `ItineraryDay` 状态结构，新增可选字段：
  - `time_blocks`：上午/下午/晚上等可执行时间段安排。
  - `route_note`：当天动线和交通策略。
  - `risk_notes`：价格、天气、体力、预约等风险提示。
- 升级 `generate_itinerary_tool`：
  - Day 1 强调抵达、入住和低强度周边体验。
  - 中间日期强调核心体验、同区域顺路延展和晚间餐饮放松。
  - 最后一天强调补漏、退房、返程缓冲和票务核验。
  - 每天都写入 `time_blocks`、`route_note`、`risk_notes` 和天气 Plan B。
- 升级 `generate_order_tool` 的报告结构：
  - 基本信息
  - 已确认资源
  - 行程亮点
  - 每日详细行程
  - 预算明细
  - 费用依据
  - 风险与出行前核验
  - 可调整项
- 增加维护测试，锁定最终报告必须包含“每日详细行程”“费用依据”“风险与出行前核验”“可调整项”“上午/”“Plan B”等关键内容。

**我的思考**

- 内容质量提升不应该只是“写得更长”，而是让信息更可执行：用户知道上午做什么、下午怎么顺路、晚上怎么收尾、下雨怎么替换、预算从哪里来、想调整该动哪一块。
- 这轮增强仍然保持工具层确定性：报告不是让模型临场发挥，而是从状态里的 itinerary、budget、transport、hotel 拼出稳定结构。
- 下一步如果继续提升质量，最值得做的是把景点和餐饮从“名称列表”升级成更结构化的 POI：区域、适合时段、预计停留、是否需预约、门票/人均、室内外属性。这样 itinerary 的动线会更真实。

## 问题 27：景点只作为名称列表传递，行程动线缺少区域、停留时长、预约和室内外属性

**状态**：已完成第一版 POI 结构化增强

**现象**

- 上一轮已经把行程和最终报告升级成更完整的交付结构，但景点仍主要来自 `attractions: list[str]`。
- 只有景点名称时，行程可以写“去外滩/上海博物馆”，但很难稳定判断：
  - 适合上午还是晚上。
  - 是否在同一区域。
  - 预计停留多久。
  - 是否需要预约或门票。
  - 下雨时能不能作为室内备选。
- 这会限制行程动线质量，最终仍可能看起来像“景点列表套时间段”。

**根因**

- `DestinationInfo` 只有 `attractions` 字符串数组，没有结构化 POI 字段。
- `generate_itinerary_tool` 只能切片景点名，无法读取区域、时段、费用、室内外属性等决策信息。
- 目的地阶段即使能查到更多信息，也没有状态字段承接这些更细的事实。

**怎么解决**

- 扩展 `DestinationInfo`，新增可选字段 `attraction_pois`。
- 新增 `POIInfo` 结构，支持：
  - `name`
  - `area`
  - `best_time`
  - `duration_hours`
  - `reservation_required`
  - `indoor`
  - `estimated_cost`
  - `tags`
- 增加 POI 归一化 helper：
  - 如果传入的是结构化 POI，就合并已知默认画像和传入字段。
  - 如果传入的是旧版字符串景点名，就自动补成基础 POI。
  - 内置上海常见 POI 画像，例如外滩、上海博物馆、田子坊、豫园、武康路。
- 升级 `generate_itinerary_tool`：
  - 时间段里展示 POI 的区域、适合时段、停留时长和标签。
  - 对需要预约/购票的 POI 增加“预约/费用提醒”。
  - 对室内 POI 增加“室内备选”提示。
  - 继续兼容旧的 `attractions: list[str]`，不会破坏已有链路。
- 增加维护测试，验证人民广场、预约/费用提醒、约 40 元/人、室内备选等 POI 细节进入行程和最终报告。

**我的思考**

- 这是内容质量从“能写”走向“会安排”的关键一步。景点名只是素材，区域、时段、停留、预约、费用、室内外属性才是行程编排的依据。
- 这轮没有直接接入新的外部 API，而是先建立项目内部的数据结构和兼容层。这样后续无论信息来自搜索、地图、人工配置还是 MCP，都有地方沉淀。
- 下一步可以继续把餐饮也结构化成类似 POI：餐厅/小吃街名称、区域、人均、适合餐次、排队风险、是否适合带娃/老人、是否需要预约。到那时 itinerary 的“吃”和“玩”就能真正按区域和时间编排。

## 问题 28：餐饮只有偏好标签，无法和景点一起按区域、餐次和预算编排

**状态**：已完成第一版餐饮 POI 结构化增强

**现象**

- 餐饮阶段原本主要记录 `selected_food_types`，例如 `local`、`specialty`、`chain`。
- 行程生成只能写“晚餐：优先匹配已确认餐饮偏好”，无法稳定安排具体吃什么、在哪个区域吃、人均多少、是否需要预约、是否可能排队。
- 这会让行程里的“吃”仍然像偏好说明，而不是能和景点动线配合的执行安排。

**根因**

- `FoodInfo` 只有餐饮类型、推荐名称列表和日均预算，没有承载具体餐饮 POI 的结构。
- `TravelState` 没有 `selected_food_pois`，用户确认具体餐饮候选后无法跨阶段保存。
- `generate_itinerary_tool` 没有餐饮 POI 输入，只能用餐饮类型标签生成泛化餐饮文案。

**怎么解决**

- 新增 `FoodPOIInfo` 结构，支持：
  - `name`
  - `type`
  - `area`
  - `meal_time`
  - `average_cost`
  - `reservation_required`
  - `queue_risk`
  - `suitable_for`
  - `tags`
- 扩展状态：
  - `FoodInfo.food_pois`
  - `TravelState.selected_food_pois`
- 扩展 `select_food_tool`：
  - 继续兼容只传 `food_types` 的旧调用。
  - 如果传入 `food_pois`，会归一化并写入 `selected_food_pois`。
- 增加餐饮 POI helper：
  - 内置默认餐饮画像，例如南京路小吃、城隍庙小吃、本帮菜餐厅、商场连锁简餐。
  - 当没有具体餐饮候选时，根据 `selected_food_types` 自动生成可用兜底餐饮 POI。
  - 格式化餐饮摘要，包含区域、适合餐次、人均和标签。
  - 生成预约/排队提醒。
- 升级 `generate_itinerary_tool`：
  - 每天午餐/晚餐会从餐饮 POI 中轮转安排。
  - `meals` 中写入具体餐饮名称、区域、人均和标签。
  - `time_blocks` 中加入“餐饮提醒”，提示预约和排队风险。
  - 最终报告的每日详细行程会自然包含这些餐饮细节。
- 增加维护测试，验证南京路小吃、本帮菜餐厅、人均 80/180 元、预约和排队风险能进入 itinerary/report。

**我的思考**

- 餐饮结构化后，行程终于不再是“白天玩、晚上吃点特色”这种泛化结构，而是可以把“吃”作为和景点同等重要的 POI 参与编排。
- 这一层先不追求真实餐厅 API，而是先确定项目内部的数据接口。后续接地图/搜索/点评类数据时，只需要把外部结果映射到 `FoodPOIInfo`。
- 下一步值得做的是把景点 POI 和餐饮 POI 做区域聚合：同一区域优先安排在同一天，不同区域避免硬凑；这会进一步提升动线真实性。

## 问题 29：景点和餐饮已经结构化，但行程生成还没有真正按区域聚合

**状态**：已完成第一版区域聚合动线优化

**现象**

**根因**

- `_pick_pois` 只是普通切片，不会优先选择和当天核心 POI 同区域的候选。
- `_pick_food_poi` 只按索引轮转，不知道当天景点所在区域，也不知道午餐/晚餐应该尽量就近。
- `route_note` 只有固定说明，没有把当天主区域和餐饮区域的匹配情况写清楚。

**怎么解决**

- 新增区域匹配 helper：
  - `_area_tokens`
  - `_areas_overlap`
  - `_format_area_list`
  - `_pick_pois_by_area`
- 景点选择从简单切片升级为“以当天种子 POI 为核心，优先补同区域 POI，再补其他候选”。
- 餐饮选择从纯索引轮转升级为带评分的选择：
  - 匹配当天主区域加权。
  - 匹配午餐/晚餐餐次加权。
  - 避免午餐和晚餐重复同一个餐饮 POI。

  - 当日主区域。
  - 餐饮是否能匹配该区域。
  - 如果餐饮候选和当天区域不匹配，会提示“如时间紧建议就近替换”，而不是假装同区域。
- 增加维护测试，验证：
  - 上海博物馆和人民公园会被安排到同一天。
  - 人民广场区域的午餐/晚餐会优先匹配人民广场区域。
  - `route_note` 会出现“当日主区域”和“餐饮优先匹配”。

**我的思考**

- 这一轮的重点不是让报告变长，而是让它更“像人真的会这么走”。旅行规划的质量很大一部分来自减少无效通勤，而不是增加景点数量。
- 我刻意保留了兼容性：如果没有区域信息，仍能按旧逻辑生成；如果有区域信息，就尽量利用。
- 我也避免了过度承诺：只有区域确实重叠时才写“餐饮优先匹配”，不匹配时明确提示可就近替换。这比硬写漂亮文案更可靠。

- `BudgetBreakdown` 只有费用分项和 `assumptions`，缺少预算可信度字段。
- `summarize_budget_tool` 没有把费用来源按“已确认/估算/待核验”分层输出。
- `generate_order_tool` 的最终报告缺少独立的预算置信度章节，风险提示也没有和预算来源直接绑定。

**怎么解决**

  - `confidence_level`
  - `confirmed_items`
  - `estimated_items`
  - `verification_items`

  - `_format_budget_confidence`
  - `_format_budget_verification_items`

  - 已确认/可追溯价格，例如具体交通方案参考价、已选酒店每间夜价格。
  - 估算项，例如餐饮 POI 人均价、景点 POI 参考门票、其他机动费用。

  - 高信息量场景应得到“中高”预算置信度。
  - 缺少交通票价和酒店价格时应得到“偏低”预算置信度。
  - 报告必须出现“已确认/可追溯价格”“估算项”“待核验项”。

**我的思考**

- 旅行规划里最危险的不是估算，而是“把估算说得像确定”。预算置信度能让系统更诚实。
- 这一步是生成质量的重要收口：行程、预算、报告不只是更丰富，而是能清楚标注信息来源和不确定性。
- 后续如果接入真实支付、真实库存或更多实时 API，可以继续把 `confirmed_items` 拆得更细，比如“实时 API 报价”“用户确认价格”“本地经验估算”。

## 问题 33：PowerShell here-string 里的中文会污染真实会话验证输入

**状态**：已确认规避方式，未改业务代码

**现象**

- 在真实主 Agent 会话验证中，直接把中文写进 PowerShell here-string 后传给 `python -`，Python 侧收到的内容可能变成 `????`。
- 模型会把 `????` 当成用户输入，导致无法识别目的地、交通方式或确认意图。
- 这会造成“工具没有被调用”的假阴性，看起来像 Agent 不会执行真实查询，实际是验证脚本输入已经损坏。

**根因**

- 当前 Windows PowerShell / 终端 / Python stdin 的编码链路不稳定。
- 中文在 shell here-string 到 Python 标准输入的过程中被错误转码。
- 这不是 Agent 业务逻辑问题，而是验证脚本入口问题。

**怎么解决**

- 本轮真实验证统一使用 ASCII-only 脚本，把中文写成 Unicode escape，例如 `\\u5317\\u4eac`，进入 Python 后再 `decode("unicode_escape")`。
- 也可以把验证脚本保存为 UTF-8 文件后执行，但如果是临时 inline 脚本，Unicode escape 更稳。
- 后续如果沉淀正式集成验证脚本，建议放入 `scripts/` 或 `tests/integration/`，文件明确使用 UTF-8 编码，避免依赖终端编码。

**我的思考**

- 真实链路验证最怕“测试输入不可信”。如果输入已经变成乱码，再分析 Agent 行为就会被带偏。
- 这类问题很隐蔽，因为日志里只看到模型没有执行正确工具，容易误判为 Prompt 或工具选择失败。
- 对需要中文多轮对话验证的项目来说，稳定的验证入口和业务代码同样重要。

## 问题 34：Windows 默认 ProactorEventLoop 与 psycopg 异步 PostgreSQL checkpointer 不兼容

**状态**：已确认规避方式，建议后续沉淀为 Windows 启动兼容逻辑

**现象**

- 真实主 Agent 验证启动 PostgreSQL checkpointer 时，出现 `Psycopg cannot use the 'ProactorEventLoop' to run in async mode`。
- 随后连接池超时：`psycopg_pool.PoolTimeout: couldn't get a connection after 30.00 sec`。
- MCP 工具本身可以启动，但主 Agent 无法完成 checkpointer 初始化。

**根因**

- Windows 上 `asyncio.run()` 默认使用 `ProactorEventLoop`。
- 当前 psycopg 异步连接池需要兼容的 selector 事件循环。
- 项目使用 LangGraph PostgreSQL checkpointer，所以真实主 Agent 会话验证必须先通过这层数据库初始化。

**怎么解决**

- 本轮验证脚本在导入并运行主 Agent 前加入：
  - `asyncio.set_event_loop_policy(asyncio.WindowsSelectorEventLoopPolicy())`
- 这样 PostgreSQL checkpointer 和 store 均可正常初始化。
- 后续建议在 Windows 专用启动入口、README 验证命令或集成测试脚本中固化这条规则，避免新会话重复踩坑。

**我的思考**

- 这不是数据库配置错误，也不是 API Key 问题，而是 Windows 异步运行时兼容性问题。
- 如果不记录下来，下一次“真实会话链路验证”很容易再次被误判成数据库连接失败。
- 更理想的做法是把真实验证脚本产品化，而不是每次临时拼命令。

## 问题 35：交通强制查询规则过宽，确认轮会重复调用真实 API

**状态**：已修复并验证

**现象**

- 航班真实链路第一轮已经正确调用 `query_transport_options`，并返回真实航班。
- 第二轮用户说“就选第一个最省心的航班，帮我记录为交通方案”时，中间件因为看到“航班”关键词，再次强制调用 `query_transport_options`。
- 最终仍能调用 `select_transport_tool` 写回状态，但多了一次不必要的真实 API 查询。

**根因**

- `_forced_tool_choice` 对 `transport_planning` 的判断过宽：只要用户文本包含“飞机/航班/高铁/火车/自驾/交通”，就强制走查询工具。
- 这对第一轮直接查询很有帮助，但没有区分“查询意图”和“确认选择意图”。
- 在真实 API 场景下，这会增加延迟、消耗额度，也可能让用户确认基于的结果和第二次查询结果不完全一致。

**怎么解决**

- 在 `app/core/middleware.py` 中增加确认/选择关键词识别：
  - `选第`、`就选`、`确认`、`锁定`、`记录` 等确认轮文本不再强制查询。
- 交通强制查询改为：
  - 用户明确说“直接查/真实/不要只口头”等直接查询关键词时强制查。
  - 或同时包含交通关键词和查询意图关键词（如“查/查询/看看/推荐/有没有/多少”）时强制查。
- 增加测试 `test_step_middleware_does_not_force_transport_query_on_selection_turn`。
- 真实高铁和航班链路复验后，第二轮确认均只调用 `select_transport_tool`，不再重复查询。

**我的思考**

- “强制工具调用”是把 Agent 从口头推荐拉回真实执行的好护栏，但护栏不能粗暴到覆盖确认动作。
- 查询轮和确认轮的边界在旅行规划里很关键：查询是获取候选，确认是把用户选择沉淀为状态。
- 这次修补后，主 Agent 的行为更像真实顾问：先查真实选项，再基于用户选择记录，而不是每次听到交通词都重新查。

- 这类问题的危险之处在于，它不是“模型坏了”，而是“项目里其实有两套模型入口”。只要模型一升级，隐藏分叉就会被放大。

- 这次统一之后，“切模型”终于从“到处找实例化代码”变成了“优先改 `.env`，必要时核对默认值和少量脚本入口”，后续维护会轻很多。

## 问题 37：交通协调器把“省心”过度放大，长途场景也会默认查询自驾

**根因**

- 之前的提示词规则是：只要用户提到“带孩子、老人、行李多、门到门、省心或不想折腾”，就让协调器同时查询自驾。
- 这条规则对“上海 -> 杭州，带老人和大件行李”非常有效，但对“北京 -> 上海”这种明显超长距离就过宽了。
- 大模型会把“省心”字面理解为“也顺手查一下自驾”，而不是结合常识先判断自驾是否值得纳入默认对照。

**怎么解决**

- 在 [app/agents/subagents/transport_coordinator.py](D:/Users/Administrator/PycharmProjects/ZhiXing/langgraph-travel-planner/app/agents/subagents/transport_coordinator.py) 中收紧规则：
  - 只有短中途或同日可轻松自驾的路线，且用户明确有门到门/省心诉求时，才默认把自驾纳入对照。
  - 对于北京-上海这类明显超长距离、跨多省、常识上自驾会非常疲劳的路线，除非用户明确要求自驾，或明确强调大量行李/老人幼儿搬运诉求，否则不要默认查询自驾。
- 新增真实联调测试 [tests/test_transport_recommendation_quality.py](D:/Users/Administrator/PycharmProjects/ZhiXing/langgraph-travel-planner/tests/test_transport_recommendation_quality.py)，覆盖：
  - 长途省时省心场景
  - 长途舒适稳定场景
  - 短途带老人/行李场景

**我的思考**

- “推荐质量”不只是最后一句推荐对不对，还包括为了得到这个推荐，系统有没有做多余的真实查询。
- 省心类诉求本来是为了让系统更像顾问，但如果规则过宽，就会让协调器在不必要的时候显得“想太多”。
- 这次把规则从“关键词触发”收紧到“关键词 + 距离常识/场景合理性”，更接近真实顾问的判断方式。
## 问题 38：Windows 下直接导入 `app.main` 时，FastAPI TestClient 仍可能回落到 ProactorEventLoop
**状态**：已修复

**现象**

- 单独跑数据库探针时，`AsyncPostgresSaver.setup()` 和 `AsyncPostgresStore.setup()` 都能成功。
- 但在 Windows 环境里直接用 `from app.main import app` 再通过 `TestClient(app)` 启动应用时，lifespan 日志里仍显示 `ProactorEventLoop`。
- 随后 `checkpointer.setup()` 会报 `Psycopg cannot use the 'ProactorEventLoop' to run in async mode`，最终表现为连接池超时。

**根因**

- 之前的 Windows 兼容逻辑主要放在 `app/run.py` 和临时验证脚本里。
- 这能覆盖“从项目推荐入口启动”的路径，但覆盖不到“测试框架或其他宿主直接 import app.main”的路径。
- `TestClient` 会自己起 AnyIO portal 线程，如果导入时没有先把全局事件循环策略切到 selector，它就可能默认落回 `ProactorEventLoop`。

**怎么解决**

- 在 [app/main.py](D:/Users/Administrator/PycharmProjects/ZhiXing/langgraph-travel-planner/app/main.py) 顶部增加 Windows 事件循环策略保护：
  - `asyncio.set_event_loop_policy(asyncio.WindowsSelectorEventLoopPolicy())`
- 这样无论是 `python -m app.run`、`uvicorn app.main:app`，还是测试/脚本直接导入 `app.main`，都会优先使用 psycopg 兼容的 selector event loop。
- 修复后重新用 `TestClient(app)` 做启动验证，`/`、`/health/live`、`/health/ready` 均可在真实 lifespan 下通过。

**我的思考**

- 这类问题很像“入口碎片化”造成的隐性回归：业务代码没变，只有启动宿主变了，系统就表现出完全不同的稳定性。
- Windows 兼容逻辑如果只放在推荐运行脚本里，仍然会遗漏掉测试、IDE、嵌入式调用这类真实场景。
- 更稳的思路是把“平台级约束”尽量放到最靠近应用入口、且最容易被所有宿主共享的地方，而不是寄希望于每个入口都记得手工补一遍。

## 问题 40：应用就绪状态仍与 MCP 冷启动强绑定，健康但偏慢

**状态**：已确认，待优化

**现象**

- 在 2026-04-30 的真实验证中，使用 `TestClient(app)` 带 lifespan 启动应用时，数据库和 Store 很快就绪，但 `/health/ready` 要等到全部 MCP warmup 结束后才会返回 `200 ready`。
- 当次验证日志显示：
  - 23:49:22 开始进入 FastAPI lifespan
  - 23:49:22 Checkpointer ready
  - 23:49:22 Store ready
  - 23:49:38 MCP warmup completed with all servers healthy
- 也就是说，在所有依赖都正常的情况下，冷启动仍大约等待了 16 秒，才能对外宣告 ready。

**根因**

- [app/main.py](D:/Users/Administrator/PycharmProjects/ZhiXing/langgraph-travel-planner/app/main.py) 的 lifespan 中，会先等待：
  - Checkpointer 初始化
  - Store 初始化
  - `await mcp.warmup()`
- 只有在这些步骤都结束后，才会把 `app.state.startup_complete = True`。
- 这说明当前的 readiness 定义不是“核心服务可用”，而是“核心服务 + 全量 MCP 热身完成”。
- 虽然 [app/mcp_core/client.py](D:/Users/Administrator/PycharmProjects/ZhiXing/langgraph-travel-planner/app/mcp_core/client.py) 已经把 MCP 探测做成了并发和降级容错，但 readiness 仍然被它整体阻塞。

**怎么改进**

- 如果目标是提高部署阶段的可用性和冷启动体验，可以考虑把 readiness 分层：
  - `/health/live` 继续只看进程是否存活
  - `/health/ready` 以数据库、Checkpointer、Store 等核心依赖为主
  - MCP 单独通过状态字段或专门接口暴露 `healthy/degraded/unavailable`
- 如果仍希望启动时预热 MCP，可以考虑：
  - 给 warmup 增加总超时或单服务超时
  - 将非关键 MCP 改为后台预热，而不是阻塞 ready
  - 为“首次请求才需要的 MCP”采用懒加载

**我的思考**

- 这不是“系统起不来”，而是“系统把 ready 的门槛设得偏高”。
- 这种设计在开发期有好处，因为一启动就知道外部工具是否齐全；但到了部署期，ready 太晚会直接影响健康检查、滚动发布和首请求延迟。
- 当前架构已经具备“降级运行”的基础能力，所以后续完全可以把“能启动”与“所有外部能力都已热身”解耦，让系统更像生产系统，而不只是联调系统。
